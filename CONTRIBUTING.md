# Contributing to Solana Microscope

Thank you for helping improve Solana Microscope.

## Before you start

- Search existing issues and pull requests before opening a new one.
- Open an issue first and wait for a maintainer to label it `accepted`. Every
  pull request has to reference such an issue with `Fixes #<issue>`; CI labels
  the ones that don't `needs-issue` and closes them, with the exception of
  typos, broken links, and comment-only fixes, which declare
  `Linked issue: trivial` in the description instead. Agreeing on the approach
  before anyone writes code is what keeps a finished change from being
  rejected on scope. Small, focused pull requests are preferred.
- Use the latest `main` branch when reproducing a problem.
- Never include secrets, private keys, seed phrases, or production credentials
  in issues, pull requests, commits, logs, or screenshots. This repository is a
  deployment template: also remove Terraform state and plan output, Grafana
  credentials, Yellowstone and RPC endpoint tokens, and identifying deployment
  data such as program IDs, vault addresses, and host names.
- All commits into a Solana Foundation repository require
  [commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification).
  CI requests changes on a pull request carrying an unverified commit and
  dismisses that review once every commit verifies.

## Security vulnerabilities

Do not report security vulnerabilities in public issues. Follow the
[security policy](SECURITY.md).

## Development setup

Install the prerequisites listed in [`README.md`](README.md#development), then:

```sh
git clone https://github.com/solana-foundation/solana-microscope.git
cd solana-microscope
cp microscope.toml.example microscope.toml
just setup
```

`just setup` configures `.githooks/pre-push`. The hook runs the maintained-code
format and lint checks before a push.

Use the toolchain versions checked into the repository (`rust-toolchain.toml`,
`Cargo.lock`, `package-lock.json`, and the pinned Carbon versions in
`Cargo.toml` and `package.json`). Do not update the Rust toolchain, the Solana
crates, the Carbon pins, container image digests, or Terraform provider
versions as an incidental part of another change.

## Generated code

Program and Squads decoders are generated by `scripts/generate-decoder.sh` and
are ignored by Git. Do not edit generated decoder crates directly.

When changing decoder generation:

```sh
just generate
just test
```

Commit the IDL, generator, lockfile, or pinned tooling changes that produce the
new output, not the generated crates.

## Making a change

A pull request should solve one problem and carry the tests, documentation, and
configuration updates needed to keep the repository usable.

Before opening a pull request:

- Run the checks relevant to your change:

  ```sh
  just fmt-check
  just lint-check
  just test
  just infra-check
  ```

  `just check` covers the maintained Rust formatting, linting, and unit-test
  suite. Cloud changes should also pass `just infra-check`.

- Add or update tests when behavior changes.
- Update public documentation and examples when configuration changes, and
  `microscope.toml.example` when you add or rename a config field.
- Regenerate derived files with the repository's documented tooling.
- Explain any new dependency and why the existing dependency set is
  insufficient.

When a change touches a trust boundary, document it: operator access to the VM
or Grafana, secret handling and rotation, network exposure, or what an alert
reveals to a notification channel. Include a threat-model note when the change
creates a new boundary.

## Pull requests

- Write a clear title and description explaining the problem, the approach, and
  how you tested it. Link related issues and call out behavior changes,
  compatibility concerns, and follow-up work.
- Use a [Conventional Commit](https://www.conventionalcommits.org/) pull
  request title, for example `feat(alerting): add email routing`.
- Confirm that no credentials or local deployment files are included.
- Fill in every section of the
  [pull request template](.github/pull_request_template.md), including the
  [AI disclosure](#disclosure). CI fails the pull request until the disclosure
  is declared.

[Greptile](https://www.greptile.com) runs on this repository. Before
maintainers review, resolve every Greptile comment with either a code fix or an
explanation of why no change is needed.

Once maintainers approve CI to run, all CI failures must be addressed before
the pull request is merged.

Maintainers may ask you to rebase, split a broad change, add tests, or revise
documentation before merging.

## AI use

You may use AI-assisted tools, but you should review the generated code,
understand its behavior, and run the same checks expected of any other
contribution.

If you are building with AI on Solana, the
[Solana Dev Skill](https://github.com/solana-foundation/solana-dev-skill) and
the [Solana MCP](https://mcp.solana.com/) can help. This repository also ships
[`CLAUDE.md`](CLAUDE.md) and [`AGENTS.md`](AGENTS.md), which carry its
conventions and gotchas; point your tooling at them rather than rediscovering
the codebase from scratch.

Ensure generated code follows the project's conventions. Maintainers can close
pull requests that appear to be low-effort AI slop. In particular, audit your
changes for the following AI code smells that increase maintenance burden:

- Comments explaining why the _previous_ behavior was wrong and the new
  behavior is correct. That context is useful as a review comment on GitHub; a
  history of every code change does not belong in the codebase.
- Large comment blocks dense with technical jargon. A comment should explain
  _why_ the code does something when that is not obvious, not _what_ it does;
  the code speaks for itself.
- Drive-by refactoring of code unrelated to the change being made.

In this repository, two AI failure modes matter especially:

- Do not paste a real deployment's `microscope.toml`, `.env`, `terraform.tfvars`
  or their values into a prompt, an issue, or a pull request. Use the example
  files.
- Do not let a tool "fix" a pinned dependency, a pinned Carbon version, or a
  deliberate deprecated call. Those pins exist for reasons recorded in
  `CLAUDE.md`; changing them is its own pull request with its own
  justification.

You must be able to explain every line of your diff without an LLM. Reviewers
may ask a pointed question about any part of the change; if the answer is
pasted from a model or does not come, the pull request is closed.

Tool attribution left in a pull request (a `Generated with Claude Code`
footer, a `Co-Authored-By: Claude` trailer, a `cursor/` or `codex/` branch, and
the like) tells us the submission was opened without being read. CI labels
these `ai-unreviewed`, fails the check, and explains what to fix. Pull requests
left in that state are closed.

### Disclosure

Disclosure is required. The pull request template has two boxes; check exactly
one. If AI tooling was used, name the tool and the extent, for example:

> I wrote all of the code for this feature, and had Claude update the
> documentation and create tests accordingly

or

> I architected the change and handed all implementation over to Codex

Editor autocomplete of single keywords or short phrases does not count as AI
tooling.

### Communication

When maintainers leave suggestions, feedback, or questions, do not paste them
into an LLM and paste the answer back. Being able to distill what AI produces
is what makes your contribution valuable.

## Releases

Releases are maintainer-driven git tags, `vX.Y.Z`. To cut one: add the section
to [`CHANGELOG.md`](CHANGELOG.md), bump the `microscope-indexer` crate version
to match, merge, then push the tag. The `Release` workflow rejects a tag whose
version does not match the crate or has no changelog section, and publishes the
section as the release notes.

Releases do not publish a container image: one image serves one program and one
IDL, so operators build or publish their own.
